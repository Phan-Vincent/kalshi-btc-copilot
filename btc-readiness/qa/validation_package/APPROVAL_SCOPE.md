# Future approval scope — proposal only

No approval is requested or recorded by this package. `QA approved` acknowledges QA review; it does not authorize prospective collection, launch, advice, schedules or execution. Candidate source stays disabled. The new executable release and its runtime destination do not yet exist as approved artifacts.

Before asking for activation approval, resolve and independently accept all of these gates:

1. Feasible evidence-supported fee/execution model, frozen before outcomes; preserve current unfavorable bound until a reviewed revision is justified. Never weaken acceptance to obtain success.
2. Coherent publication and interrupted-run/restart contract, including cross-store partial commits and pending observations.
3. Boot/suspend and trusted clock recovery design, hardware power-loss/durability verification or explicitly accepted bounded operation.
4. Measured long-run capacity/HTTP-body/archive growth, implemented disk/quota/IO halt and approved evidence retention. Proposed capacity values are not safeguards yet.
5. Current official source/fee/rate/fill-precision/entitlement attestation for approved read-only data, including any authenticated BRTI reads.
6. Separately reviewed new-study validator/release, locked deployment dependencies and final source/config/protocol/package manifest; do not repurpose the disabled candidate or study 002 approval.
7. Holdout access custody, complete required calendar/evidence, release/settlement rechecks and no automatic promotion.

Any later approval must name all of the following concrete values in one reviewable action:

- Final distinct study ID; currently proposed `btc-prospective-005-20261214-PROPOSED`.
- Absolute new release and new runtime paths, final source/config/dependency/protocol/package SHA256s, and supported host/storage environment. No destination is preapproved here.
- Future UTC start, validation, holdout, end, release and approval deadline, with approval timestamp before deadline. Proposed start is December 14, 2026 UTC; missed deadline requires a new reviewed proposal, no automatic shifts.
- Evidence-only source endpoints/access scope, fixed polling/request pacing/rate quotas, any separately authorized read credentials, capacity/body-size/storage/retention/restart limits and stop behavior.
- Holdout custodian/access boundary, result-release authority and named stop authority; no protected prior outcome access or cohort reuse.
- Exact permitted launch action and whether any scheduler/service change is separately included. Schedule creation or service activation is not implicit in generic QA approval.

Explicit exclusions must remain: real orders or simulated-as-live orders; order creation/cancellation/modification; leverage/account/fund mutations; BTC position advice or personalized sizing; original/sealed release/config/state changes; inherited approvals; holdout-driven tuning or primary reselection; automatic repairs/backfills/deletions/restarts, dates or promotion outside separately approved scope.

This proposal cannot be used as an `activation_approval.json`. No future action should proceed merely because package integrity tests pass. A changed hash/date/design requires a new concrete review, with existing evidence preserved.
