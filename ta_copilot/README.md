# BTC TA Copilot (read-only, descriptive)

A live technical-analysis view for the Kalshi KXBTC15M series. It is separate from the Study 005 candidate and the Acer study stack, and it does not change the advice gate: **Paper only; no orders or portfolio or balance reads.** An optional scope-checked, read-only Kalshi API key is used only for its own scope check, the market-data WebSocket and BRTI backfill. Without it, public REST and the composite proxy remain in use. The experimental paper scalp trigger (mean reversion, then `momentum_v1`) ran 2026-10-03 07:14–08:14 UTC and was **retired by the owner on 2026-10-03**; its code, report and pre-removal snapshot are in `history/retired_scalp_20261003/` (on the Acer: `~/btc-ta/retired_scalp_20261003/`), and its journal stays on the Acer at `~/btc-ta/state/scalp_log.jsonl` as a record. The no-direction rule applies again without exception.

## Where it runs

On the Acer, as the user service `btc-ta-copilot.service` (restarts on failure; linger keeps it up without a login). It listens on `127.0.0.1:8770` and is published tailnet-only by Tailscale Serve:

**https://homelab.example-tailnet.ts.net:11443/**

```sh
acer/deploy.sh remove   # stop/disable services and remove Serve mapping (files stay in ~/btc-ta)
ssh acer 'journalctl --user -u btc-ta-copilot -n 50'

```

## Run locally

```sh
python3 ta_copilot.py            # http://127.0.0.1:8770/
python3 ta_copilot.py --port 8771
```

The Acer uses its system Python `websockets` (16.1) and `cryptography` (46.0.5) packages. If a socket drops, REST polling takes over. Local keyless tests need only the Python standard library; signature tests skip when `cryptography` is unavailable. The page loads lightweight-charts 4.2.3 from unpkg with an SRI pin; the dashboard code is served separately as `/app.js` with `Cache-Control: no-store`. Every response has a Content-Security-Policy that allows the pinned chart script, the page's inline stylesheet, the data-URL favicon, and same-origin state requests, plus `nosniff` and `no-referrer` headers.

## Optional Kalshi key

Place `key_id` (one line) and `private_key.pem` in `~/.config/btc-ta-copilot/kalshi/`, or set `TA_KALSHI_KEY_DIR` to another directory. The directory and private key must be owned by the service user and inaccessible to group and others (for example, directory `0700`, private key `0600`). The key may be Ed25519 PKCS#8 or RSA. Before the first authenticated market-data connection, the service checks that this exact key has nonempty read-only scopes. A write scope immediately disables it; failed scope checks retry with bounded backoff. The key ID, key material, signatures and headers are never served or logged. The deploy script does not copy credentials.

Kalshi settles KXBTC15M on the mean of the 60 one-second BRTI values at seconds `close−60 … close−1`. In an offline comparison of 2,342 windows, this mean reproduced `expiration_value` to $0.01; the four-venue composite proxy missed by $2.63 median and was on the wrong side of the target in 36 of 1,889 windows. BRTI is a settlement reference, not a forecasting signal. `/api/state.brti` reports configured, connected, value, source age, freshness, our complete 60-second mean, and BRTI minus composite. `feed_modes.Kalshi` names WebSocket, REST fallback, or keyless. The Kalshi card labels the settlement basis and orderbook source. Minute research rows add `brti` and `brti_age`; close rows add `brti_avg_60s` and `brti_samples`. Existing composite and proxy fields retain their old meanings. `tally_report.py --calibration` adds a BRTI-close-versus-expiration comparison; the default report and PRIMARY remain unchanged.

## What it shows

- **Spot**: Coinbase Exchange BTC-USD WebSocket ticker and matches feed. A REST ticker takes over if the socket is unavailable or its newest trade is over 10 s old; it runs on its own 2 s thread, so slow candle requests can't delay it. Kraken is treated the same way: the WebSocket counts as active only while its newest trade is fresh, and a replayed or out-of-order trade never moves the Kraken quote back. Every spot update patches the forming bar on each timeframe, and may open at most 3 bars past the newest fetched candle, so it can't bridge a gap in history.
- **Composite spot proxy**: median of fresh Coinbase, Kraken, Bitstamp and Gemini BTC-USD last trades. A ticker older than 10 s or more than 0.5% from the fresh-venue median is excluded. The Kalshi card shows each price, its difference from the composite, age, inclusion status and a rolling 60 s mean from contiguous 1 s composite samples. Kraken uses trade time on WebSocket and fetch time on REST; Gemini uses fetch time. At each window close, the server records our own 60 s composite mean over the settlement minute (seconds close−60…close−1) as a `close` row. Once Kalshi settles, it compares that mean with Kalshi's `expiration_value` (the BRTI 60 s average). The spot card shows the median and 90th-percentile absolute error and the bias over the latest 200 complete windows (`proxy_record` in `/api/state`; "too few to judge" below 20). The displayed composite and average are unchanged until the PRIMARY test is evaluated. The page also shows included venues out of four, the price range across included venues, and a degraded label for single-venue operation. Each venue age names its basis: exchange timestamp, trade, or successful fetch. The error metrics cover the latest scored windows; a separate coverage line partitions all recorded closes into scored, incomplete samples, awaiting settlement (Kalshi's value not published yet and still being asked for), unavailable settlement value, or invalid proxy (exclusive reasons, checked and listed in that order). Only closes awaiting settlement can still be scored. This denominator covers recorded closes, not windows that were never recorded.
- **Candles**: Coinbase Advanced Trade public market candles (1m/5m/15m/1h, 300 bars each), refreshed every 10–120 s. **10m** has no native granularity, so it's aggregated from 600 five-minute bars (about 2 days), fetched as two 300-bar pages that meet without a gap (before 2026-10-07 one 5m bar at the seam was always missing). A 10m bar missing any of its 5m bars, other than the forming one, is marked `partial` and counts as a gap in `history`. The Exchange `/candles` endpoint lags several minutes, so it isn't used. A response is rejected whole, keeping the last good history with a `candles_<tf>` error, if it is empty, older than the history already held, or has any bar with a nonpositive or nonfinite price, low > open/close > high, negative volume or a misaligned time. Each frame carries `history` (`lag_seconds`, `stale`, `gap`): `stale` means the newest fetched bar ended more than one bar plus 120 s ago, `gap` means bars are missing among the last 60. The derived 10m frame is never fresher than its 5m source: it is stale or gapped whenever 5m is. `/api/state` lists `history_stale` and `frames_unavailable`, minute rows record `history_stale`, and the page shows a note above the chart. Stored readings and votes are not changed by these flags. On the page, stale or gapped history suppresses the affected directional summaries and reading badges, with a reason; the historical chart stays visible. The headline always requires the 1m frame and never substitutes another timeframe. Spot/composite staleness or more than 10 s without an accepted snapshot also suppresses the summaries until fresh data arrives.
- **Kalshi window**: the open KXBTC15M market from the public `/markets` endpoint, polled every 2 s. If that listing lags at rollover, the prefetched next ticker is shown immediately and triggers a direct public `GET /markets/{ticker}` without waiting for the next poll; direct requests for a ticker stay at most once every 2 s. If listing, prefetch and cache all miss, the dashboard derives the current slot's ticker from its New York close and checks it directly only after `/exchange/status` explicitly says open. The direct result must match the ticker and exact 15-minute slot. The card quietly names any source other than the listing. It says "Target pending" until `floor_strike` arrives. It shows the countdown, YES/NO bid and ask, and distance from the target in the settlement-average proxy model described below.
- **Order flow**: public Coinbase matches and Kraken trades produce cumulative taker buy minus taker sell BTC volume since the current 15-minute open, a trailing 60-second split and imbalance, a trailing 3-minute taker split and imbalance, and large-trade markers. The 3-minute reading does not vote; before full coverage it is labelled "first N s of window" (coverage starts at the later of window open and connection). A trade whose notional, or the window's resulting volume, would not be a finite number is rejected (`invalid` counter), so absurd upstream sizes can't make the served state unserializable. The default marker threshold is `$25,000` notional; `TA_LARGE_TRADE_USD` can change it. A partial-window label appears if earlier trades are unavailable.
- **Kalshi context**: YES/NO best-bid depth and implied ask depth with up to five levels per side, the YES spread and mid, recent trades, and descriptive book and tape summaries. With a checked key, an in-sequence WebSocket snapshot and deltas supply the book; a gap, stale connection or missing snapshot restores the public REST book GET. A WebSocket trade subscription starts for the next market 60 s before its open. Trades are deduplicated by ID against the REST tape. REST paging stops only when its coverage bridges the WebSocket subscription start (or the subscription predates the open) and the trade sequence stays intact. A gap or disconnect restores REST paging and its existing coverage rules. `complete_window`, `complete_60s` and `fresh` keep their prior meaning. The page state reads the in-sync WebSocket book live, not at the 2 s context poll. Kalshi numbers the `ok` acknowledgement of `add_markets`/`delete_markets` with the next `seq` on that subscription (seen live on 2026-10-27), so it is counted rather than treated as a gap. Trades for the next market that arrive before the dashboard promotes it (the first came 0.9 s after an open) are held and adopted into its tape. A numbered control frame out of sequence counts as a gap too. WebSocket trades received while REST still owns the tape stay pending across gaps and reconnects, so they never count as REST overlap; a bridge needs a REST trades request started after the subscription was acknowledged. A trade that moves the context to a new market also drops the previous market's book and mid path. With a key, the YES mid path gains one point per second from the live book (it holds a whole window); keyless, it keeps the 2 s REST cadence. Mid, microprice and tape are descriptive and not executable.
- **Window in context**: follows the selected timeframe. It shows candle closes over a matching lookback (1m → 15 min, 5m → 1 h, 10m → 2 h, 15m → 3 h, 1h → 12 h), then the 1 s composite path inside the current Kalshi window (shaded, with the time still left shown as space on the right), plus the target across the whole view. Beside it: time left, composite minus the rolling 60-second average, and the high and low since the window opened.
- **Browser delivery**: `/api/stream` pushes state with Server-Sent Events. State is computed once per timeframe per roughly one-second cache lifetime and shared with `/api/state`. At most 12 SSE clients are admitted; additional clients receive HTTP 503 and the page falls back to `/api/state` polling. A slot is released however the connection ends, including a drop while headers are sent; sockets time out after 30 s without progress. The watcher still uses `/api/state`.
- **Indicators per timeframe**: EMA 9/21/50/200, RSI 14 (Wilder), MACD 12/26/9, Bollinger 20/2 (%B, width), ATR 14, Stochastic 14/3, anchored VWAP (from the Kalshi window open on 1m; from the first loaded bar otherwise), and support/resistance zones (see Levels). The ATR row also names a volatility regime from ATR 14 divided by the median of its last 60 values: expanding at 1.3 or above, compressed at 0.7 or below, normal between; unavailable before 60 values. The regime does not vote.
- **Levels**: zones from fractal swing pivots on the viewed timeframe plus higher native timeframes (10m only on its own tab), and session highs/lows (prior UTC hour, today and the prior UTC day, and the window open). Clustering uses a neighbour tolerance of 0.25 × ATR 14 (minimum $5); zones are at most 0.5 × ATR 14 wide (minimum $10). Round $500 numbers and the anchored VWAP (Coinbase-only volume) only add confluence tags and never make a level. The strength score is touches weighted 1m 1 / 5m 2 / 10m 2 / 15m 3 / 1h 4, +1 per session source, +1 per tag. An MTF tag means swing touches came from at least two distinct higher native timeframes; it does not change strength or the logged levels summary. Stale or gapped frames are excluded and listed. Distances, roles and the target check use the composite (spot only when unavailable). Zones also show crossings of the zone mid by closed bars of the viewed timeframe since the first touch. An at-price zone shows its prior role and distances to its lower and upper edges. A zone counts toward the target only when wholly between the composite and target. The window open is used only when its path was observed from the open; session highs/lows require complete bars, with skipped sessions listed; the nearest two zones per side are drawn on the chart. Levels do not count in the tally, family vote or PRIMARY and are **unvalidated**. There is no volume profile: candle volume is Coinbase-only and cannot place volume at a price inside a bar, and the trade stream only covers the current window since restart.
- **Tally**: each reading is bull, bear or neutral. The lean is shown only when one side leads by 2 or more. RSI/Bollinger extremes count as neutral ("stretched") rather than as reversal calls. The tally is **unvalidated** and is not a trade signal.
- **Family vote** (2026-10-03): below the legacy count, one vote each for **trend** (EMA stack, EMA 9/21, EMA 200, MACD and VWAP; it votes when 3 or more of the 5 agree), **momentum** (RSI 14 inside 30–70) and, on 1m only, **flow** (60 s taker imbalance at ±0.20 or beyond). Flow votes only once 60 s of the current window have passed; before that, the page shows "Flow warming up" and the vote is neutral. The opening record always has a neutral flow vote and keeps the measured partial imbalance as context. It shows the net (bull families minus bear families) and a family lean when |net| ≥ 2. Bollinger %B, Stochastic and stretched RSI appear as muted **context** rows and never count toward families. The legacy count and lean are unchanged, so old and new records compare directly. Under the lean, a track-record line shows how the legacy 1m lean at window open has scored against settlement, with its Wilson 95% interval (`tally_record` in `/api/state`).

- **Live stream** (`/api/stream`, SSE, 1 event/s): a full state on connect, on a Kalshi window change and once a minute; other events carry only the newest 5 points of each series, merged by time in the page (about 17 KB/s per open tab). The page falls back to polling `/api/state` if SSE fails. The page judges freshness on its own clock: if no snapshot has been accepted for 10 s the badge reads "No update for N s", a silent stream is closed, and polling runs until a reconnected stream delivers. Polls never overlap, have a 5 s deadline and are aborted on a tab switch; a snapshot for another timeframe, or older than the one shown, is dropped. When the selected timeframe has no history, spot, Kalshi, flow and errors still update and the chart says the frame is unavailable. If the server can't serialize its state it sends a `problem` event (badge "Server state error"). A failure ("Warming up", "Server unreachable", "Server state error") stays on the badge until a new healthy snapshot is accepted; the clock only ages it. The badge also warns when the 1m history is stale, because 1m always supplies the headline tally: the headline then says so and the timeframe table marks each stale or gapped column with ⚠, whichever tab is selected.

## Caveats

- Kalshi settles on the 60-second CF Benchmarks BRTI average. This four-venue composite and its average remain proxies, **not BRTI**, and retain their research meaning. The displayed distance in σ is a Brownian settlement-average proxy, not a probability. With fresh BRTI (source age at most 2 s), the distance uses BRTI before the final minute and a projected BRTI settlement mean inside it. Otherwise it uses the existing composite path. The 1m realized σ still comes from Coinbase candles. The window's and minute rows' `sigma_1m_usd` stays composite-based (the dollar scale of σ at the composite); only the displayed distance and its scale use BRTI. The separate rolling composite average stays unavailable until it has a full contiguous minute of valid samples.
- The page shows STALE when Coinbase's exchange trade time is more than 10 s old, its last update is more than 20 s old, or the composite is unavailable. A lagging Coinbase stream triggers REST fallback. Kalshi freshness is separate: `window.age` measures time since the last successful public Kalshi fetch carrying the displayed window, from the listing or direct ticker endpoint. `kalshi_stale` becomes true after 10 s without one, except for a five-second grace when a prefetched window is first promoted. A failed GET does not refresh this timestamp; a continued outage at rollover becomes stale when the grace ends. The window card shows the metadata age when it exceeds 10 s, the header badge turns amber when `kalshi_stale` is true, and an expired market is hidden. When no market is listed, `/exchange/status` is checked at most every 30 s. If Kalshi explicitly reports the exchange or trading inactive, the page shows "Kalshi exchange closed", `kalshi_stale` is false, and both the Acer watcher and off-Acer alarm skip the stale-Kalshi alert. A failed status check counts as open. Socket reconnects use bounded backoff while REST keeps retrying. Order flow is descriptive market data, not a trading recommendation.
- In the final minute, observed seconds are the BRTI seconds at `close−60 … now−1` when BRTI is fresh; missing ended seconds are filled with current BRTI for the projection. A second is due only once it has ended. The card separately shows the mean of actually held BRTI seconds and its count, marking it complete only at 60. For 30 seconds after close, that complete value is shown as the **BRTI settlement average**, not a result. The required remaining average and constant slope still describe a hypothetical straight-line path with one sample per remaining second (`k = 1..R`); they are not probabilities. When BRTI is stale, the old composite projection and wording remain in use. The historical composite proxy error is a separate measure.

## Health alerts and research log

`btc-ta-watch.timer` runs every five minutes as a separate Acer user timer. It checks the dashboard service, `/api/state`, `stale`, feed errors older than 10 minutes, candle history stale on any timeframe (`history_stale`), and a Kalshi window that has been missing or stale (`kalshi_stale`) across checks spanning 8 minutes (the third check in a row). With a Kalshi key configured and scope-checked, it also alerts when BRTI has not been fresh (`brti.fresh`) across checks spanning 8 minutes, since the settlement figures then fall back to the composite proxy; it skips this while Kalshi reports the exchange closed, and a missing key directory (keyless by choice) never alerts. A refused key or a failing WebSocket also shows up as a `kalshi_key` or `kalshi_ws` feed error after 10 minutes. A `systemctl` failure is reported as "service status unknown" and the API is still checked. An unreadable or malformed state file is renamed `ta_watch_state.corrupt-<time>` and the watcher starts fresh. It sends a `[BTC TA]` Telegram message on a problem, recovery, and every six hours while unhealthy. This deployment does not send an installation test message. The watcher reads the existing Acer Telegram configuration locally and keeps its own state in `~/btc-ta/state/` with private permissions. It does not send a daily alive message. Its state file is rewritten after every completed run, and `/api/state` reports that file's age as `watcher_age`, so the off-Acer alarm can tell when the watcher itself has stopped.

**Off-Acer alarm (Mac).** The Acer's own watcher can't report the Acer being down. `acer_watch.py` runs on the Mac from a LaunchAgent every five minutes. It checks that the Acer answers over Tailscale (TCP 22 on its MagicDNS name) and that the dashboard at `:11443` is ready, not stale, and has a current Kalshi window, and that the Acer watcher has completed a run in the last 15 minutes (`watcher_age`). A damaged state file is set aside (`state.corrupt-<time>`) instead of stopping the checks. It sends `[ACER]` messages on a problem after **two consecutive failing checks**, on recovery, and every six hours while unhealthy. If the Mac can't reach `api.telegram.org`, it does nothing and keeps its state. It runs only while the Mac is awake; if the Mac's own Tailscale is down, it reports the Acer unreachable. Install with `mac/install_acer_watch.sh` (`status`, `remove`). That needs the Telegram config copied from the Acer to `~/.config/btc-study/telegram.json` (0600). The installer copies the script to `~/.local/share/btc-acer-watch/`, because launchd jobs can't read `~/Documents`.

The dashboard prefetches the next public market and captures composite spot and indicators at its scheduled opening. Kalshi may still show the market as `initialized` then, with no target or usable YES quotes. In that case, the snapshot is held privately in `~/btc-ta/state/tally_pending.json`; after the public target appears, one `open` line is appended to `tally_log.jsonl`. The line distinguishes `captured_at` from `target_observed_at`, and leaves opening YES bid/ask null if no valid quote existed at capture. It includes the per-timeframe tally, RSI, MACD histogram, family votes, `family_net` and `family_lean`, plus the 60 s flow imbalance and the 1m realized σ in dollars (`sigma_1m_usd`). After settlement, a separate `settled` line includes the public `result` and `expiration_value`. Because readers keep the first `settled` row per ticker, the line is held until `expiration_value` is published, for up to 30 minutes after close (`SETTLE_VALUE_WAIT`); after that it is written with the result alone, and the server keeps asking for up to 24 hours (`SETTLE_VALUE_RETRY`, resumed after a restart). A value that arrives later is appended as a `settled_value` row, which every reader merges into the settled row. A restart in the middle of a window does not label a late snapshot as an opening observation. Logging runs in its own thread and has no effect on the dashboard response. Settled windows beyond 500 are folded into running counts without changing the track record or proxy coverage. The latest 200 scored closes, pending opens and awaited settlement values are kept. The log on disk is untouched, and startup still reads all of it. A failed append (a full disk, say) never stops that thread: an `open` or `close` row that could not be written stays queued and is retried every second, with a `tally_log` or `tally_close` feed error shown until it succeeds (the watcher alerts if that lasts 10 minutes).

`log_tools.py check PATH` counts rows, unreadable lines, duplicates and missing windows. `log_tools.py merge PRIMARY SECONDARY -o OUT` merges two logs (primary rows win, except that a primary `settled` row without `expiration_value` takes the value from a secondary row with the same result; output 0600; it never overwrites). At startup, in the offline report and in `log_tools`, unreadable log lines are skipped and counted; later valid rows still load. All three use one schema check (`tally_report.record_problem`): a non-empty string ticker, an integer minute, a dict of frames with integer `family_net`, parseable ISO timestamps, integer bull/bear/neutral counts present together, and finite numbers. Numbers the server writes itself must be JSON numbers; only Kalshi's `expiration_value` and YES quote prices (which early minute rows stored as decimal strings) may be numeric strings, and never "NaN" or "inf". On 2026-10-07 this rejected 0 rows in the real logs. A row that fails it counts as unreadable, so `log_tools merge` leaves it out. An append repairs a missing trailing newline before writing the next row. The first valid `open` and `settled` row per ticker wins in both readers. The dashboard track-record line and the report show skipped-line counts. ISO timestamps with any fractional-second length are accepted; timestamps without a zone are read as UTC.

Inside each window, one `minute` line is appended at each whole minute 1–14 (written only within 2 s of `:00`; a restart never backfills missed minutes). It records the ticker, minute, seconds left, composite, 60 s average, target, 1m σ, fresh YES bid and ask with their age (null when stale or missing), the 1m flow imbalance, the stale flags, and every timeframe's legacy tally, family vote and `levels` summary (nearest support/resistance, touches and ATR distances, at-price flag, zones to target and target-in-zone flag). It records no outcomes and makes no Kalshi request of its own. Each row is roughly 2.5 KB, so the log grows by about 3.5 MB a day.

```sh
ssh acer 'cd ~/btc-ta && python3 tally_report.py'
```

The report is descriptive only, and the dashboard never reads it. Its sections:

- **Legacy:** the original per-timeframe opening-lean hit rates with Wilson 95% intervals, flagging samples under 100.
- **Size of the move:** the Spearman correlation of the opening net score with settlement value − target, with a bootstrap interval.
- **Minute horizon:** the 1m `family_net` against the next 1 and 3 minutes of composite and YES mid, with mean change by net value and a block bootstrap that resamples whole windows.
- **Market:** the legacy 1m lean against the market's side near open. Kalshi usually has no quote at `:00`, so this uses the minute-1 mid.
- **Proxy vs settlement:** our closing-minute composite mean against Kalshi's `expiration_value` over all complete windows, with the median and 90th-percentile absolute error, the bias, the maximum, and how many incomplete windows were left out.
- **Levels:** exploratory 1m nearest-zone crossings over the next 3 minutes by ATR distance, counted only from the zone’s own side, with 95% block-bootstrap intervals over windows. The target comparison uses the minute-1 row only, with Wilson intervals, and lists why windows were excluded. Suppressed readings are excluded.
- **PRIMARY:** one pre-declared test, the Spearman correlation of 1m `family_net` with the next 3-minute composite change, over the first 800 windows with minute rows. It is evaluated only on or after 2026-10-14 00:00 UTC and reports "CI excludes 0" or "CI includes 0". The selected windows stay in open-time order through the bootstrap, so the result is identical on every run (before 2026-10-07 it depended on Python's string-hash seed). Run with `--manifest primary_manifest.json` when evaluating it, to keep the selected tickers, the seed and round count, and SHA-256 digests of the log, the selection and `tally_report.py`. With `--manifest`, the log is first copied once to `primary_manifest.input.jsonl` (0600), and both the report and the manifest are computed from that copy, so rows appended meanwhile can't make them disagree and the exact input is kept.
- **Calibration (`--calibration` only):** exploratory observed YES settlement rates by minute-row σ-distance bucket and fresh YES-mid 10¢ bucket, plus minute-14 composite-side lock-in accuracy, with counts and Wilson 95% intervals. It is offline, descriptive, and does not appear on the dashboard. The default report is unchanged.

Every other section is labeled exploratory. With about 1,000 windows the report takes roughly half a minute to run.
