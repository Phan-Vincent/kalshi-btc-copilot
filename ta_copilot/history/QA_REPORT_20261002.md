# Adversarial QA: live BTC TA dashboard — 2026-10-02

All times below are UTC. This was read-only QA of `https://homelab.example-tailnet.ts.net:11443/` and isolated Mac tests. No dashboard source, Acer service, or Tailscale setting was changed. No Telegram path, Kalshi account or order route, or study path was called. The three deployed source hashes matched this folder on 2026-10-02 at 01:35 UTC (`ta_copilot.py` `df20ead6…`, `stream_flow.py` `e06141f7…`, `index.html` `7f8076df…`). Commands and selected outputs are embedded so the evidence survives the temporary capture files. The live comparisons used public unauthenticated GETs. The market's official [Kalshi rules](https://kalshi.com/markets/kx/m/kxbtc15m-26aug060715) specify the final 60-second BRTI average; the dashboard's four-venue series is a proxy.

## Findings

| ID | Severity | Title | Evidence | Suggested fix |

## Evidence

### E01 — expired market remains Live (F01)

Command: `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=$PWD python3 /private/tmp/ta_qa_local.py` against an isolated `Feed` seeded from the 01:19:52 live state; `get_json` was monkeypatched to raise for Kalshi URLs. Selected output at 01:23:51:

```text
Kalshi GET failure {'ticker': 'KXBTC15M-26OCT012130-30', 'left': 368.457, 'market_age': 1.004, 'yes_bid': 0.32, 'stale': False, 'errors': {'kalshi': {'error': 'OSError: injected Kalshi timeout', ...}}}
after cached close {'ticker': 'KXBTC15M-26OCT012130-30', 'left': 0.0, 'market_age': 1.006, 'yes_bid': 0.32, 'stale': False, 'errors': {'kalshi': {'error': 'OSError: injected Kalshi timeout', ...}}}
```

The second row sets only the cached close time to one second before the test's clock; no Acer state was changed. `poll_market` leaves `self.market` in place on exception (`ta_copilot.py:680-708`); `state` still builds a window and clamps time to zero (`:802-812`). `stale` checks spot/composite only (`:854`). The client uses that flag for the green Live badge and does not display `window.age` (`index.html:418-420`, `:473-475`). The error is relegated to footer text.

### E02 — settlement scale and reference (F02)

Command: `python3 -u /private/tmp/ta_qa_sigma.py` made two live GETs; independent calculation used the served 1m candles and sample standard deviation of 60 log returns, then multiplied by the displayed composite. Output:

```text
2026-10-02T01:28:05.109833Z left=114.89s strike=84648.28 composite=84556.645 past_60s_avg=84576.498 display_distance=-71.782 display_z=-1.690 sigma_1m_usd=30.698 endpoint_sd=42.480
2026-10-02T01:29:05.074018Z left=54.93s strike=84648.28 composite=84565.400 past_60s_avg=84562.154 display_distance=-86.126 display_z=-2.924 sigma_1m_usd=30.781 endpoint_sd=29.451
```

The formula at `ta_copilot.py:126-130, 823-832` switches to the **past** rolling 60-second composite when two minutes remain, then divides by `σ_1m × √(seconds_left/60)`. Kalshi instead settles on the **last** minute's BRTI average. At 114.89 seconds left, that future minute has not begun; the past proxy average differs from the current composite by $19.85. Under an illustrative Brownian 1m diffusion model, the future average's standard deviation is `σ × √((114.89−60)/60 + 1/3) = $34.30`, while the displayed endpoint scale is $42.48, **24% larger**. At 54.93 seconds left, part of the settlement minute is already observed; its remaining uncertainty is `σ × √((54.93/60)^3/3) = $15.57`, versus $29.45 displayed, **89% larger**. These are model comparisons, not validated probabilities; the unmeasured BRTI/proxy basis adds uncertainty. The live `distance` and `distance_sigmas` arithmetic matched the code, so the issue is the quantity's interpretation.

### E03 — countdown skew (F03)

Command: Node evaluated the actual `tick()` body from `index.html:403-412` with the live state captured at `2026-10-02T01:19:52.750773Z` and a `Date` clock shifted by ±30 seconds. Output:

```text
server_left 607.25  clock_skew_s -30  display 10:37 left
server_left 607.25  clock_skew_s   0  display 10:07 left
server_left 607.25  clock_skew_s +30  display 9:37 left
```

`server_time` is available, but the client subtracts the browser's uncorrected `new Date()` from `close_time`. Near expiry, a fast client clock can show 0:00 before the true close.

### E04 — flat RSI (F04)

Command: `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=$PWD python3 /private/tmp/ta_qa_local.py` with 300 identical $100 candles and zero volume. Output at 01:23:51:

```text
flat bars {'rsi': 100.0, 'bb_pctb': None, 'sigma': 0.0, 'atr': 0.0, 'stoch_k': 50.0, 'vwap': 100.0}
```

The `rsi` branch returns 100 whenever average loss is zero, including when average gain is also zero (`ta_copilot.py:214-229`). That displays an overbought extreme for a no-change series. The zero-width Bollinger and zero-sigma paths produced null/zero finite values rather than NaN in this case.

### E12 — stale Coinbase ticker appears fresh (F12)

Command: isolated `Feed` with three current $84,600 venue quotes and one Coinbase ticker whose exchange `time` was 60 seconds old and whose price was $80,000; `handle_coinbase_message`, `sample_composite`, then `state('1m')`. Output at 01:43:10:

```text
spot 80000.0  spot_age 0.0  spot_trade_time 2026-10-02T01:42:10.804068Z
coinbase_venue {'price': 80000.0, 'age': 60.0004, 'included': False, 'excluded_reason': 'stale'}
composite 84600.0  stale False
```

`venue_quote` rejects future timestamps but not old ones (`ta_copilot.py:75-93`). `update_spot` sets `spot_at` to receipt time (`:482-487`), so `state` declares the spot fresh from that time (`:849,854`) while its own composite logic excludes Coinbase as stale. The displayed spot, bid/ask, percentage changes, and indicator readings can therefore use a price the page otherwise recognizes as stale. This was an injected delayed public ticker, not observed on the live feed.

### E05 — real rollover (F05)

The page says “No open window” when `window=null` (`index.html:351-354`), though spot remains Live. The tally log, read with `ssh acer` and Python JSON parsing, contained `settled` for `...2130-30` and `open` for `...2145-45`, captured at `01:30:00.051078Z` and target observed at `01:30:10.157947Z`. Thus the research logger knew the next target about 19 seconds before the page selected the next ticker. `poll_market`'s `status=open` list and active-time filter (`ta_copilot.py:680-690`) are a plausible cause; this capture alone does not isolate the upstream list delay.

The second real boundary repeated the behavior. The old `...2145-45` window showed `0:00` at `01:45:00.143279Z` and `01:45:01.204861Z`; `window=null` from `01:45:02.171653Z` through `01:45:22.234369Z` (21 one-second samples); the new `KXBTC15M-26OCT012200-00` appeared at `01:45:23.291340Z`, target `$84,553.06`, `path_partial=false`. Flow reset to CVD 0/trades 0 at `01:45:00.143279Z`, then accumulated trades during the blank window. A separate public `GET /markets?series_ticker=KXBTC15M&status=open&limit=20` every two seconds returned no new market at `01:45:20.049442Z`, then returned the new active ticker at `01:45:22.054495Z`; the page followed about one second later. Thus the second gap largely reflected the public `status=open` listing delay. The tally log had already captured the new opening at `01:45:00.052466Z` and observed its target at `01:45:07.735668Z`; by `01:46:18Z` it also had the previous window's `settled` line.

### E06 — NaN breaks both delivery paths (F06)

Command: same isolated local script as E01, bound only to Mac `127.0.0.1:8781` and shut down after GET probes. A valid ticker price and time with `best_bid='NaN'` passed `handle_coinbase_message`; output:

```text

/api/state HTTP 200 bytes 300 contains_NaN True

/api/stream HTTP 200 bytes 0
```

`float()` accepts `NaN` for bid/ask, while `venue_quote` validates only the last price and time (`ta_copilot.py:75-93, 513-524`). `/api/state` uses permissive `json.dumps` (`:1115`), which yields invalid browser JSON; SSE uses `allow_nan=False` after sending HTTP 200 and does not catch `ValueError` (`:1088-1108`). This is an upstream-malformed-input failure reproduction, not an observed live Coinbase `NaN`.

### E08 — sampler delay misclassified (F08)

Command: isolated `Feed` seeded with a live state, four venue quotes still inside 10 seconds, and `composite_at=now−3`; then `state('1m')`. Output at 01:32:33:

```text
composite None stale True venue_included {'Coinbase': True, 'Kraken': True, 'Bitstamp': True, 'Gemini': True}
```

`state` calculates current venue inclusion but discards that recomputation (`ta_copilot.py:779`), then blanks the cached composite after 2 seconds and sets `stale=true` (`:796-798, 854`). A short sampler pause therefore hides still-fresh market data for that request.

### E09 — missing book side suppresses fallback (F09)

Three further direct live order-book GETs at 01:40:40, 01:40:53, and 01:41:05 found both sides, but the best YES bid moved by 1–3 cents between each dashboard state and the following direct GET 0.3–0.5 seconds later. That movement is normal timing uncertainty, not an arithmetic mismatch, and underscores why quote age/source should stay explicit.
