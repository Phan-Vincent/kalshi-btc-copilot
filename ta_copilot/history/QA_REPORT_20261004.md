## Evidence

### E01 — stale composite

`scripts/reproduce.py` supplies a ready but `stale=True` state with `composite=100`; `minute_record` writes both values, and `forward_changes` uses a stale minute as the start of a $50 change:

```text
stale_forward [(1, 50)]
stale_logged 100 True
```

`ta_copilot.py:1154-1160` records the stale flag but does not null the composite. `tally_report.py:191-206` checks only for non-null endpoint composites. This can affect the exploratory correlations and PRIMARY. An actual outage was not induced.

### E02 — missing intermediate rows

`forward_changes({"W": {1: row(1,100), 4: row(4,130)}}, 3)` returns:

```text
gap_1_to_4 [(1, 30)]
```

Minute 2 and 3 are absent. `tally_report.py:195-199` checks only `minute+horizon`, even though the task requires no bridging across missing minutes. The current unit test checks an endpoint gap for horizon 1, but expects the 1→4 result for horizon 3.

### E03 — duplicate minute after restart

The reproduction creates a logger, captures at open+60.5 s, creates a new logger for the same state directory, calls `prepare()`, and captures at open+61.0 s:

```text
restart_same_minute [('W', 1), ('W', 1)]
```

`TallyLogger.prepare` skips minute lines (`ta_copilot.py:1212-1215`); `minute_captured` starts as `None` (`:1196`) and is the sole dedup state (`:1329-1334`). `tally_report.load_rows` currently keeps the first minute for statistics, so the duplicate does not inflate its `n`, but the raw research record violates the promised one-row-per-minute invariant. No backfill of a missed minute occurs.

### E04 — readers disagree on conflicting duplicates

The reproduction writes two `open` rows for ticker X, first bullish and then bearish, plus two YES `settled` rows:

```text
duplicate_conflict dashboard 0 1 report 1 1
```

`TallyLogger.prepare` overwrites `opened[ticker]` and `results[ticker]` with the last row (`ta_copilot.py:1217-1221`). `tally_report.load_rows` uses `setdefault`, retaining the first (`tally_report.py:57-63`). The dashboard's `tally_record` and the offline legacy section therefore disagree. This requires a conflicting log, whose likelihood was not measured; the inconsistency is deterministic once one exists.

### E05 — contradictory settlement fields

With target 100, `result=yes`, `expiration_value=99`, and a bullish opening lean:

```text
contradictory_settlement 1 move -1.0
```

`summarize` scores a hit from `result` (`tally_report.py:84-89`), while `settlement_moves` derives a negative move from `expiration_value-target` (`:176-188`). No consistency check joins these fields. A malformed or revised upstream settlement can thus create incompatible statistics without a warning. The synthetic record does not establish that Kalshi has emitted one.

### E06 — 50¢ has no directional market side

At YES bid .49 and ask .51, the mid is exactly .50. The bullish lean is counted as disagreeing with the market:

```text
market_exact_50c Leaning windows with a market price: 1; lean on the market's side: 0
```

`tally_report.py:303` uses `price > 0.5`, assigning equality to NO. The 45–55¢ inclusive band itself is correct (`MARKET_BAND=(.45,.55)`).

### E07 — partial flow can create a lean

Three bull trend readings, no momentum reading, and flow imbalance +1 yield:

```text
short_flow_family {'votes': {'trend': 'bull', 'momentum': 'neutral', 'flow': 'bull'}, 'net': 2, 'lean': 'bullish'}
```

`Feed.sample_composite` advances and resets flow at the window boundary before `_capture_open` (`ta_copilot.py:714-752`). During the first 60 seconds, `OrderFlow.rolling` uses only trades since the new window open (`stream_flow.py:784-827`). `family_tally` accepts the imbalance without coverage (`ta_copilot.py:476-496`); the family display (`app.js:220-222`) and saved minute schema (`ta_copilot.py:1147-1160`) have no duration field. The separate flow card says observed from window open but does not label the family vote's sample length. The scheduled minute-1 row at about open+60.5 s is near a full minute; the misleading early vote primarily affects the live family line.

### E08 — torn line recovery

Appending an incomplete `{"type":"open"` after a valid minute line yields:

```text
torn_prepare JSONDecodeError Expecting ',' delimiter: line 1 column 15 (char 14)
torn_report JSONDecodeError Expecting ',' delimiter: line 1 column 15 (char 14)
```

`TallyLogger.prepare` catches only `FileNotFoundError` (`ta_copilot.py:1208-1233`), so its `refresh_record` and pending-open load are skipped; `run()` catches the error and continues (`:1348-1353`). `tally_report.load_rows` also catches only a missing file (`tally_report.py:49-66`). `append` uses a single append-mode write and private mode 0600 (`ta_copilot.py:1280-1288`), but a crash or short write can leave a partial final line. The synthetic truncation proves recovery behavior, not an observed write tear or concurrent interleaving.

### E09 — naive date

```text
naive_primary TypeError can't compare offset-naive and offset-aware datetimes
```

`primary_result` compares a caller's `now` directly against an aware UTC constant (`tally_report.py:322-329`). The CLI supplies `datetime.now(timezone.utc)`, so normal CLI runs avoid this failure. A local-time aware `now` compares correctly as an instant.

### E10 — missing family evidence

`analyze` omits EMA200 until 200 bars exist and can omit RSI for insufficient bars (`ta_copilot.py:420-430`). `family_tally` still requires 3 bull or bear trend readings and turns absent RSI into `momentum: neutral` (`:476-496`). Saved rows contain only votes/net/lean (`:1090-1118`, `:1147-1160`). Thus 3-of-4 trend evidence and 3-of-5 evidence, or absent RSI and RSI=50, look identical in the saved family object. This is a transparency issue; the absolute 3-vote threshold itself matches the specification.

### E11 — opening flow baseline is not neutral

`opening_record` was given a snapshot captured 0.2 s after market open with a flow imbalance of +.25. It produced:

```text
opening_flow 0.2 0.25 bull
```

`_capture_open` passes `self.flow.rolling(at).get("imbalance")` into the opening snapshot (`ta_copilot.py:754-775`), and `opening_record` passes it into `frame_family` (`:1090-1104`). A trade in those first seconds can therefore change the opening `family_net`/`family_lean` that will later be compared with settlement, even though README says flow is neutral in the opening record. This is especially sensitive because the opening flow may comprise one trade. The existing test `test_opening_record_has_families_and_sigma` actually asserts a bull opening flow for a +.25 input; it does not verify the README baseline.

## Other checks that passed

- **Legacy tally:** `scripts/reproduce.py` compared current and baseline `analyze` on 40-bar and 250-bar flat, ramp, and wave series. All four legacy tally dictionaries matched exactly. The source diff adds family logic outside `analyze`; `test_tally_20261003.py` also covers legacy continuity. The prescribed exact RSI boundary values 55/45/70/30 and MACD zero were not forced independently.
- **Family arithmetic:** current tests cover trend 3-of-5, RSI context, flow at inclusive ±.20, absent flow off 1m, and |net|≥2. Opening, minute, `/api/state`, and page use the same `family_tally` output; the page's headline family is always the 1m frame (`app.js:211-222`).
- **Quote freshness:** `minute_record` nulls a missing or >10 s YES side and all sides when `kalshi_stale`; the targeted test passes. `state()` attaches a book only when its ticker matches the current market (`ta_copilot.py:1033-1044`). A real rollover quote comparison was unavailable.
- **Report math:** `scripts/stat_checks.py` compared 400 tied random cases with SciPy; maximum absolute Spearman difference was `2.22e-16`. `n<3` and constant inputs returned `None`. The first-800 primary gate returned `False` before 2026-10-14 UTC, `True` afterward with 800 windows, and retained identical rho/CI when a later window was added. It uses chronological `open_time` when present, falling back to the first minute timestamp.
- **Bootstrap:** `block_bootstrap` resamples whole windows with replacement, recomputes Spearman on concatenated rows, and uses a fixed seed (`tally_report.py:123-143`). The 200-log calibration and limits appear below.
- **Settlement and market arithmetic:** signed move is `expiration_value-target`; sigma scaling uses `sigma_1m_usd*sqrt(15)`; market fallback uses minute-1 mid. Opening and minute prices are parsed from their different schemas. The 45–55¢ band includes both edges. Duplicates are deduplicated by ticker/minute in the offline loader, subject to G04.
- **Record cache:** `refresh_record` iterates the in-memory opened/results maps on the logger thread, without reading the log or blocking the HTTP state/SSE path. It flags fewer than 100 scored windows and uses Wilson 95%. At 2 MB/day, the file would be about 60/180/360 MB after 30/90/180 days; `prepare()` scans it at startup, while an ordinary refresh visits about 2,880/8,640/17,280 opened windows if 96 open per day.
- **Logger timing and settlement polling:** `minute_record` rejects minute 0 and 15 and samples only within 2 seconds after each whole minute; the restart test confirms missed earlier minutes are not backfilled. `settle_pending` runs on the logger thread no more often than its 60-second scheduler, so it does not issue repeated GETs for one ticker faster than 2 seconds. It will retry unresolved tickers on future cycles; no never-settling ticker or large backlog was timed here.
- **Front end:** The new family sink uses only server-defined family keys/states; track-record uses `textContent`. The context strip defines 15m/1h/2h/3h/12h lookbacks and draws the target across the full view. When the window is null, it shows no observations; when `kalshi_stale`, it still draws the old in-window path and the header badge flags staleness. No confirmed new upstream-string HTML injection was found by source review. No trade direction call, winning probability, or automation was found in the new display/report code; non-primary report sections are marked `[exploratory]`.

Calibration used 200 synthetic logs per condition, each with 800 independent windows × 14 autocorrelated minute observations, the actual `block_bootstrap`, seed 20261003, and 30 resampling rounds per log to bound runtime (`scripts/calibrate.py`). Under the null, 14/200 CIs excluded zero (7%; mean rho −0.0001). With a planted effect whose mean observed rho was +0.0805, 200/200 excluded zero. Seven percent is compatible with roughly 5% at this sample size, but 30 rounds make percentile tails coarse; this is a smoke calibration, not a precise coverage guarantee. The simulation uses correlated contemporaneous observations rather than the full price-path `forward_changes` transform, so it does not validate that transform.
